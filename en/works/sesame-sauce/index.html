Background

This project strings together commonly used back-end middleware to simulate a high-concurrency video application, carefully replicated to the spec of https://www.bilibili.com/ and deployed on Alibaba Cloud ECS. It handles a full stateful, async-pipelined system: video upload, transcoding, HLS segment streaming, full-text search, like counters, and more. A pile of infrastructure (MySQL / Redis / Kafka / Elasticsearch / object storage / FFmpeg) is organized into an evolvable and replaceable engineering structure.

What I did

Full-stack implementation, front-end / back-end separated:

  • Front-end (Vue 3.5): Composition API + <script setup>, Vite 8 build, Element Plus component library, hls.js for m3u8 streaming, Axios + Vue Router.

  • Back-end (Go): Gin + GORM, four-layer architecture (Handler / Application / Domain / Infra).
  • Video processing: FFmpeg / FFprobe transcoding, cover generation, video analysis, dispatched asynchronously via Kafka.
  • Storage & search: MinIO object storage + Elasticsearch full-text search + Redis (incl. RedisBloom Cuckoo Filter for dedup / counter caches).

Technical highlights

  • Domain layer with zero infra coupling: domain/ defines only port contracts — six ports including VideoStorage, VideoAnalyzer, CoverGenerator, VideoTranscoder, and SearchIndexer — and imports no concrete tech package. Infra implementations carry compile-time checks (var _ domain.VideoStorage = ...). Replaceability via dependency inversion: swapping MinIO for Alibaba Cloud OSS only requires adding a new port implementation.
  • Application-layer orchestration: chains multiple domain operations into complete use cases (e.g., create video → generate presigned URL → dispatch Kafka event), and manages cross-DAO transactions and DTO conversion.
  • Multi-bitrate HLS transcoding: FFmpeg produces two renditions (1080p/5000k and 360p/800k) plus a master.m3u8, with hls.js switching adaptively on the client. The transcode flow is idempotent against duplicate Kafka deliveries. Upload cancellation is a synchronous status flag: the transcode consumer polls it and kills the running FFmpeg process via context.

  • Dual-bucket storage & concurrent upload: raw videos go to a private bucket with presigned-URL direct upload; HLS outputs go to a public bucket (presigning can’t cover m3u8’s sub-segment requests). Transcoded segments are uploaded by an 8-worker pool — any failed segment cancels the whole batch.
  • Fully async like pipeline: likes are buffered through Kafka for traffic shaving, with a per-user-per-video SetNX short lock against duplicates, three-level dedup (Cuckoo Filter + Redis pending + DB), and a Lua script that atomically syncs Redis counters only when the DB row actually changed. A 30s fallback flush task sweeps dirty ZSet entries straight into the DB, with retries landing in a dead-letter hash.
  • Counter cache architecture: like/view counters use a base + delta two-layer design — requests only write the Redis delta, and a flush task triggers on a hybrid condition (every 60s or ≥1000 dirty keys), atomically zeroing deltas with GETDEL under a Redis distributed flush lock. Failures roll back the delta and retry; after 3 attempts entries go to a dead-letter hash.
  • Multi-tier cache defense: Redis caches video details, play history, and like history. Jittered TTLs prevent cache avalanches; a SetNX mutex + Lua script releases locks atomically so only a single request hits the DB, preventing hot-key breakdown; a Cuckoo Filter intercepts illegal keys to prevent cache penetration.

  • Search with graceful degradation: Elasticsearch recalls hashids, then MySQL handles ordering and pagination; on ES failure the query automatically degrades to a LIKE fallback. Indexes and mappings are created/upgraded idempotently at startup.
  • Systematic concurrency optimization: WaitGroup parallelization runs through the whole pipeline — dual presigning on video creation, dual HEAD checks on upload confirmation, five parallel queries for unread counts, and parallel DB writes + ES indexing on the consumer side. Writes update only specific columns to avoid GORM Save full-row overwrite races.
  • ID obfuscation & auth: Hashids exposes non-enumerable video / user IDs; JWT handles user auth; a read-fanout model powers system-notification delivery, including like and comment notifications.

Results

  • A complete, runnable video platform covering upload, transcoding, streaming, search, and engagement.
  • A clean four-layer architecture with port contracts; infrastructure is smoothly swappable.
